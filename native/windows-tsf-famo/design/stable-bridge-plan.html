稳定 TSF Bridge + 可独立更新 Runtime：免重启常规升级方案

目标读者：执行本方案的 AI 代理（Codex）。
仓库：famotype-win，全部路径相对 native/windows-tsf-famo/。
日期：2026-07-30。

0. 一句话

进程架构已经是三段式，不需要重新设计。要做的是：把 FamoTextService.dll（Bridge）从版本目录里拆出来放到稳定路径、只在 Bridge 自身变化时才替换它，并让 IPC 协议支持「旧 Bridge × 新 Runtime」的版本协商。这样常规升级只换 Runtime 侧文件，宿主进程里加载的 DLL 不动，不再触发 PendingReboot。

1. 现状与根因

1.1 现有架构（勿改）

宿主进程 (Explorer / 浏览器 / 终端…)
  └─ FamoTextService.dll        ← 进程内 TSF TIP，不加载引擎（已验证：text-service/src 无 LoadLibrary/引擎依赖）
       │  命名管道 runtime-v2 / control-v2（endpoint 名稳定，不含版本目录路径）
       ▼
FamoRuntime.exe                  ← 独立进程，可随意杀/重启
  ├─ FamoRimeEngine.dll / rime.dll   ← 引擎，仅 Runtime 进程加载
  └─ 候选窗/状态栏渲染 (runtime-protocol/src/candidate_window.cpp)

1.2 为什么现在升级要重启

  • 安装器每次升级提取到新的不可变目录 {app}\versions\<version>-<manifest-prefix>-<txid>，五个二进制全部在内，包括 FamoTextService.dll。
  • COM InprocServer32 / TSF profile 每次升级重指到新版本目录里的新 DLL。
  • 宿主进程锁着旧 DLL → 安装器（正确地）拒绝形成新旧混用的 Ready，切离注册后进 PendingReboot（见 installer/README.md 事务顺序一节）。
  • 协议层无兼容窗口：runtime-protocol/src/protocol.cpp:115 对帧头 version 做严格相等校验（version != kProtocolVersion → InvalidFrame），所以即使保留旧 DLL，也只有协议版本恰好没变才能工作。

结论：重启是安装策略 + 协议无协商造成的，不是进程架构问题。

2. 不变式（验收的最高标准）

I1 — 常规升级不碰 Bridge。只要新旧安装包的 Bridge 载荷（FamoTextService.dll）SHA-256 一致，升级事务不得替换、移动、反注册该 DLL，不得改动 COM/profile 注册，不得进入 PendingReboot。
I2 — Bridge 变更是显式例外。Bridge 载荷变化时，走现有的完整事务（重注册 + 被锁则 PendingReboot），机制原样保留，只是从每次升级的必经路变成罕见路径。
I3 — 旧 Bridge × 新 Runtime 必须可用。Runtime 必须接受协议版本在兼容窗口内（至少 [N-1, N]）的 Bridge；新增宿主行为一律走 capability/state_flags 位，旧 Bridge 不认识的位表现为功能缺失（优雅降级），不是断连。
I4 — Runtime 重启 = 会话重建。换 Runtime 期间打字线程有界失败开放（已有 bounded IPC），Bridge 自动重连新 Runtime 并重建会话；进行中的组字被清除，不残留候选窗。此行为已有基础（smoke RECOV 行），升级路径复用它。
非目标：不做 DLL 热卸载/热替换（TSF 进程内 DLL 无法安全卸载）；不做双 Bridge 并存注册；不引入 shim/detour 链；不把 TSF profile 所有权移出 Bridge（RUNTIME-BOUNDARY-AUDIT.md 既有非目标继续有效）。

3. 目标布局与注册

现状目标
Bridge DLL{app}\versions\<ver>-…\FamoTextService.dll，每次升级换路径{app}\bridge\v<bridge-abi>\FamoTextService.dll，路径只随 bridge-abi 号变化
COM InprocServer32 / profile每次升级重指指向 bridge 稳定路径，仅 bridge-abi 变化时重指
Runtime/引擎/配置/工具继续用 {app}\versions\<ver>-… 不可变目录（不变）
payload-manifest单一 manifest 五个二进制拆两段：bridge 段（DLL + bridge-abi 号）与 runtime 段（其余四个 + payload）；两段各自带 SHA-256 清单
管道 endpointruntime-v2/control-v2 名字稳定（不变，这正是 Bridge 不需要知道 Runtime 路径的原因）

bridge-abi 是一个手工递增的整数（起始 1），存在 bridge 段 manifest 里，也编进 DLL 的文件版本资源。它不是产品版本号：产品 1.5.x → 1.9.x 期间它可以一直是 1。

4. 协议兼容策略

  • 帧头校验放宽：protocol.cpp 解析端把 version != kProtocolVersion 改为 version < kMinSupportedProtocolVersion || version > kProtocolVersion。新增 kMinSupportedProtocolVersion（当前 = 2）。写端继续写自己的 kProtocolVersion。
  • Hello 协商：Hello 请求带 Bridge 的协议版本与 bridge-abi；Hello 响应带 Runtime 的协议版本。双方取 min(bridgeVer, runtimeVer) 作为会话协议版本，之后按该版本编解码。字段追加到 Hello 载荷尾部，旧解析器忽略多余字节即可兼容（若现有解码是严格长度校验，则允许尾部多余字节仅对 Hello 放宽）。
  • 兼容窗口政策：Runtime 必须支持 [N-1, N]；发版时若要抬 kMinSupportedProtocolVersion，必须先发一个 bridge-abi bump（走 I2 例外流程），不允许在 runtime-only 升级里抬门槛。
  • 新功能路由：一切新宿主行为优先做成 Runtime 侧逻辑；确需 Bridge 配合的，走 Composition::state_flags 高位 capability bit（现有 kHostInlinePreedit 等即此模式），旧 Bridge 对未知位的行为必须是忽略。
  • 失败开放：版本协商失败（窗口外）时 Bridge 按现有 Unavailable 路径处理——按键透传、不阻塞打字线程，健康探针报 Degraded。

5. 分阶段实施

Phase 1 — 协议兼容窗口（先做，纯 runtime-protocol 侧）

改动：

  • runtime-protocol/include/famo_runtime_protocol.h：加 kMinSupportedProtocolVersion；Hello 载荷追加 bridge_protocol_version、bridge_abi 字段（尾部追加）。
  • runtime-protocol/src/protocol.cpp：解析端版本区间校验；Hello 编解码更新；会话协议版本落到连接状态（runtime_server.cpp / 客户端侧连接对象）。
  • runtime-protocol/tests/protocol_selfcheck.cpp 与相关合同测试：新增「version = N-1 的帧被接受」「窗口外被拒且 Status 语义不变」「Hello 尾部多余字节被旧解析器忽略」用例。

验收：自检/合同测试通过；现网协议 v2 帧 100% 不受影响（回归现有全部 runtime-protocol 测试）。

Phase 2 — 安装器：runtime-only 快速升级路径

改动（installer/famo-setup.iss + build-installer.ps1 + manifest 生成）：

  • manifest 拆 bridge/runtime 两段（§3）。
  • 升级事务开头新增判定：读当前 Ready generation 的 bridge 段 SHA-256，与新包 bridge 段比对。一致 → 走新的 runtime-only 事务：提取新版本目录（不含 Bridge DLL 或含但不注册，取实现简单者，推荐不含）、停旧 Runtime、启新 Runtime、--control deploy、回读校验、写 Ready；全程不触碰 COM/profile 注册与旧 Bridge DLL。不一致 → 走现有完整事务（I2）。
  • runtime-only 事务的回滚 = 停新 Runtime、重启旧版本目录的 Runtime；不涉及注册恢复，比现有回滚短。
  • 旧版本目录清理：runtime-only 升级成功后，旧版本目录里没有被宿主锁定的文件（Bridge 不在其中），可按现有清理规则直接删。

过渡处理：从「Bridge 还在版本目录里」的旧版（≤1.5.6）升上来的第一次，Bridge 路径必然变化 → 必然走一次完整事务（可能 PendingReboot）。这是最后一次强制重启，README 与升级提示里明说。

验收：settings-winui/FamoSettings.Tests/InstallerContractTests.cs 新增合同用例——bridge 段一致时事务日志不得出现反注册/重注册步骤、终态不得为 PendingReboot；smoke-harness.ps1 增加一行「宿主开着记事本组字中 → 覆盖安装新 runtime-only 包 → 不重启、打字恢复、版本号变新」。

Phase 3 — Bridge 稳定目录迁移

改动：

  • 安装器把 Bridge 装到 {app}\bridge\v<bridge-abi>\，COM/profile 指向它；版本目录不再含 Bridge。
  • Test-FamoHealth.ps1 / Test-FamoTsfRegistration.ps1：注册路径校验从「当前版本目录」改为「当前 bridge-abi 目录」，并校验 bridge 段 manifest hash。
  • 卸载：bridge 目录纳入现有「被锁则登记重启删除」逻辑（复用现状语义）。

验收：连续两次 runtime-only 升级后，{app}\bridge\v1\FamoTextService.dll 的 NTFS 对象 ID/时间戳不变；健康与注册探针全绿。

Phase 4 — Bridge 变更节流制度（流程，不是代码)

  • 仓库加一页 design/BRIDGE-FREEZE.md：列 Bridge 的职责白名单（TSF 编排、edit session、UIElement facade、管道客户端、失败开放），任何 PR 想改 text-service/ 必须回答「为什么不能放 Runtime 侧」。
  • CI/合同测试断言：bridge-abi 未 bump 时 FamoTextService.dll 导出表与协议引用面不变（最低限度：bridge 段 hash 变化 ⇒ 要求 commit message/manifest 同时 bump bridge-abi，安装器构建脚本硬校验）。

6. 测试矩阵（最终必须全绿）

#场景期望

T2窗口外版本拒连，Bridge 失败开放透传按键，健康报 Degraded

7. 执行顺序与边界

  • 顺序：Phase 1 → 2 → 3 → 4，每个 Phase 独立可发版、独立回归。Phase 1 不依赖安装器改动，先合。
  • 只允许触碰：runtime-protocol/、installer/、settings-winui/FamoSettings.Tests/、健康/注册探针脚本、design/。不动 text-service/ 热路径（除非 Phase 1 的 Hello 字段要求 Bridge 侧编码器同步，那也仅限编解码调用点）。
  • 本仓有多个 AI 会话并行开发：动手前 git status + 看近期 log；当前工作区已有 famo-setup.iss、InstallerContractTests.cs、dev_profile_main.cpp 的未提交改动，先确认归属再开工。
  • 每个 Phase 宣称完成前：跑该模块既有测试 + 本文对应验收行，带输出证据。
